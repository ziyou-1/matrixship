# 小红书获客采集数据过滤设计

## 1. 背景与根因

获客中心的小红书采集结果存在主页链接为空或 `-`、用户名为空、用户名等于评论、同一用户重复出现，以及评论末尾混入时间、地区、作者、点赞和回复控件文本的问题。

根因位于 `backend/platform_adapters.py` 的评论 DOM 采集和归一化链路：

- 选择器把 `.comments-container` 和 `.comment-list` 下的普通 `div` 也当作评论候选节点。
- 候选节点的全部文本先被压成一行，再按第一段为用户名、其余内容为评论进行猜测。
- 归一化阶段不校验主页链接、用户名与评论的一致性。
- 当前去重键为“用户名 + 评论”，同一主页发布不同评论时仍会重复。

假数据基线冒烟已经复现：现有 `_xhs_normalize_comment()` 会接受无主页链接、空洞用户名、用户名等于评论以及带 `赞 回复` 尾部元信息的数据。第一次在 Windows 终端输出 emoji 样例时遇到 GBK 编码错误，改用 UTF-8 标准输出后复现成功；实施前需要把该冒烟记录同步到 `docs/TROUBLESHOOTING.md`。

## 2. 已确认需求

- 在本地后端采集阶段过滤，不依赖前端隐藏。
- 无有效小红书主页链接的记录一律过滤。
- 用户名为空时过滤。
- 用户名与清洗后的评论内容完全相同时过滤。
- 用户名为 `.` 或纯 emoji 时，只要主页链接有效就保留。
- 评论末尾的时间、地区、`作者`、`赞`、`赞N`、`回复`属于无用元信息，需要清除。
- 评论正文中自然出现的“赞”或“回复”不得误删。
- 同一主页链接只保留一条记录：优先保留意向等级最高的评论；等级相同时保留点赞数更高的评论；仍相同时保留先采集到的评论。
- 每条被过滤或被去重淘汰的数据都要记录结构化日志。
- 日志不得记录原始用户名、评论内容或完整主页链接，只记录原因、笔记 ID、字段长度和不可逆指纹。

## 3. 方案对比

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| A. 只在获客结果返回前过滤 | 改动最少 | `/api/xhs/comments` 仍返回脏数据，错误解析继续存在 | 不采用 |
| B. 收紧 DOM 解析，并在采集层统一清洗、校验、去重 | 从源头修复，所有小红书评论消费者得到一致结果，不改变 API 契约 | 选择器变化可能减少低置信度评论数量 | 采用 |
| C. 拦截小红书私有评论接口响应 | 字段通常更完整 | 依赖私有接口、签名和风控策略，长期稳定性与合规风险高 | 不采用 |

不引入新框架或数据库。现有 Python、Playwright、`unittest` 和 `utils.structured_log.json_log` 已能覆盖该修复，新增依赖没有收益。

## 4. 数据流与组件边界

修复后的数据流如下：

1. `xhs_get_comments()` 只采集明确的评论行，保留 DOM 文本换行和主页链接。
2. 纯函数解析用户名和评论正文，不把回复区、操作按钮或相邻评论拼接进正文。
3. 评论清洗器只删除末尾可识别的小红书元信息。
4. 校验器规范化主页链接，并按已确认规则返回有效记录或稳定原因码。
5. 单笔记内按规范化主页链接归并。
6. `discover_xhs_leads_by_keyword()` 跨笔记再次按主页链接归并。
7. 排序、意向筛选和现有 API 响应结构保持不变。

过滤发生在 `backend/platform_adapters.py`，因此 `/api/xhs/comments` 和 `/api/finder/discover` 都不会再输出已定义的无效记录。前端 `FinderPage` 不增加兜底过滤，避免后端脏数据被其他消费者继续使用。

## 5. 解析与清洗规则

### 5.1 DOM 候选

- 优先使用类名或属性明确表示评论项的节点，例如 `comment-item`、`CommentItem` 和评论语义属性。
- 不再把评论容器内的所有普通 `div` 直接作为候选。
- 每个候选必须能解析出 `/user/profile/` 主页链接，否则交给校验器过滤并记录日志。
- 浏览器脚本保留原始换行；Python 解析器从独立文本行中识别用户名和第一条评论正文，后续回复不并入主评论。

### 5.2 主页链接

有效主页链接必须满足：

- 协议为 `http` 或 `https`。
- 主机为 `xiaohongshu.com` 或其子域名。
- 路径匹配 `/user/profile/{user_id}`，且 `user_id` 非空。

去重键使用规范化后的主页路径，忽略查询参数和片段。API 返回继续保留可打开的 HTTPS 主页地址，但不保留用于追踪或签名的查询参数。

### 5.3 评论尾部元信息

清洗器从字符串尾部向前匹配，只删除连续出现的以下元信息：

- `刚刚`、相对时间、`MM-DD`、`YYYY-MM-DD`。
- 与时间相邻的地区信息。
- `作者` 和可选分隔符。
- `赞`、`赞N`、`回复`。

清洗器不得在正文中间做全局替换。例如“求回复一下”“这个回答值得赞”必须原样保留。

## 6. 校验、去重与原因码

校验顺序固定，确保同一输入得到稳定原因码：

| 原因码 | 条件 |
|---|---|
| `missing_profile_url` | 主页链接为空或为 `-` |
| `invalid_profile_url` | 链接不是有效小红书用户主页 |
| `empty_user` | 规范化后的用户名为空 |
| `user_equals_comment` | 用户名与清洗后的评论完全相同 |
| `duplicate_profile` | 同一规范化主页已有更高或同等优先级记录 |
| `duplicate_profile_replaced` | 当前记录更优，先前记录被淘汰 |

记录优先级依次比较：意向等级 `高意向 > 中意向 > 咨询 > 普通`、点赞数、采集顺序。不同主页即使用户名相同也不合并。

## 7. 结构化日志与脱敏

复用 `utils.structured_log.json_log`，新增事件：

- `xhs_collected_record_filtered`：每条校验失败记录。
- `xhs_collected_record_deduplicated`：每条去重淘汰记录。
- `xhs_collection_filter_summary`：每个笔记采集完成后的汇总。

单条日志包含：

- `reason`
- `noteId`
- `candidateIndex`
- `userLength`
- `commentLength`
- `recordFingerprint`
- `profileFingerprint`，仅链接可规范化时存在
- `errorId`，沿用 `json_log` 自动生成

指纹使用 SHA-256 后截断展示，不可反推出原文。日志不传入原始用户名、评论、完整主页链接、Cookie、Authorization 或查询参数。解析异常使用同一结构化日志工具并附带经过脱敏的异常堆栈。

## 8. 配置、兼容与回滚

新增环境变量 `XHS_STRICT_LEAD_FILTER_ENABLED`，默认开启。设置为 `0`、`false`、`no` 或 `off` 时，仅关闭新增的严格校验和主页级归并，用于误过滤时的紧急降级；不会修改数据库或历史记录。

实施时同步更新 `backend/.env.example` 和 `docs/DEPLOYMENT.md`。完整回滚恢复以下文件的修复前版本：

- `backend/platform_adapters.py`
- `tests/test_xhs_lead_filtering.py`
- `backend/.env.example`
- `CHANGELOG.md`
- `docs/DEPLOYMENT.md`
- `docs/IMPLEMENTATION.md`
- `docs/TROUBLESHOOTING.md`

本次不改变请求或响应 JSON Schema，不需要修改 OpenAPI、`API_REFERENCE.md` 或 `migration.sql`。

## 9. 非功能性要求

| 项目 | 目标 |
|---|---|
| QPS | 本地单节点按用户触发串行采集，沿用现有限流；不新增外部请求 |
| 过滤延迟 | 300 条候选的纯 Python 清洗、校验和归并低于 5 ms，测试环境允许低于 50 ms |
| 内存 | 单次过滤额外内存低于 5 MB |
| GPU/显存 | 0 MB，不使用 GPU |
| 可观测 | 每条过滤和去重记录有脱敏 JSON 日志，每个笔记有汇总日志 |
| 可回滚 | 环境开关可关闭严格过滤；代码和文档可按文件级回滚 |
| 可追溯 | 测试固定原因码，`IMPLEMENTATION.md` 使用最终行号，`CHANGELOG.md` 记录变更 |

## 10. 测试策略

### 10.1 Phase 0 假数据冒烟

先建立最小采集后处理骨架，输入包含以下记录的假数据：

- 无主页链接。
- 空用户名。
- 用户名等于评论。
- 有效主页链接且用户名为 `.`。
- 有效主页链接且用户名为纯 emoji。
- 评论末尾含时间、地区、作者、`赞N` 和 `回复`。
- 两条相同主页但意向或点赞数不同的记录。

期望只输出有效用户，清洗后的正文不含尾部元信息，并保留优先级最高的重复用户记录。

### 10.2 失败测试先行

新增 `tests/test_xhs_lead_filtering.py`，先确认以下测试在现有代码上因缺少行为而失败：

- 评论尾部元信息被删除，正文自然用词被保留。
- 无链接、无效链接、空用户名、用户名等于评论分别返回稳定原因码。
- `.` 和纯 emoji 用户名在链接有效时通过。
- 相同主页保留高意向记录；同等级保留高点赞记录；完全相同时保留第一条。
- 不同主页的同名用户不会合并。
- 过滤日志是可解析 JSON，不包含样例用户名、评论、完整链接或查询 token。
- 严格过滤环境开关可恢复兼容行为。

### 10.3 回归与冒烟

- 运行新增测试并确认从红到绿。
- 运行现有小红书、结构化日志和本地任务相关测试。
- 对 `backend/platform_adapters.py` 执行 Python 编译检查。
- 使用假数据再次运行端到端后处理冒烟。
- 条件允许时使用已登录测试账号采集一条笔记，只验证读取，不执行评论、发布或其他外部写操作。

真实小红书页面受登录状态、IP 风控和 DOM 变化影响。如果无法完成真实页面冒烟，最终报告必须明确说明未验证部分及残余风险。

## 12. 验收标准

- 获客中心不再展示无主页链接、空用户名或用户名等于评论的记录。
- `.` 和纯 emoji 用户名在主页有效时正常展示。
- 评论末尾不再带时间、地区、作者、点赞和回复元信息，正文自然用词不受影响。
- 同一小红书主页最多出现一次，并按已确认优先级保留记录。
- 每条被过滤或去重的数据都有脱敏结构化日志，日志中没有用户原文或完整链接。
- API 响应字段、抖音获客链路和前端展示代码不发生行为回归。
- 相关测试、编译检查和假数据冒烟通过，真实页面验证结果被明确记录。
